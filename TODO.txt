7. Reverse lookup: given a function, find which vtable slots (across which structs) point to it.
	Useful for finding all the ways a virtual function can be reached. Needs a database-wide

8. Handle vtable pointers hoisted into a local variable before the call, e.g.:
		v1 = tcb->field_vtable;
		v1->Func_18(tcb);
	instead of the direct 'tcb->field_vtable->Func_18(tcb)' form. JumpToImplementation's check()
	requires the call's function expression to be a member access of another member access
	(e.x.op in [cot_memptr, cot_memref]); when the vtable pointer comes from a local var instead,
	e.x is a cot_var and the action doesn't even show up, let alone find the VTABLE: comment(s)
	on the original member. Would need to trace the local var back to its defining assignment
	(walk the function body for the cit_expr/cot_asg that set it, similar in spirit to how
	SetVtable already walks up from a clicked expression to find its enclosing assignment) and
	resolve that RHS the normal way. CommitType's vtable-slot editing is unaffected by this
	(it only needs the vtable struct's own member, which get_member_struct_and_offset already
	finds correctly through a local var); this is specifically a JumpToImplementation problem
	(and, by extension, anything built the same way in the future).

9. Properly support a base class with a shorter vtable than an extension class. A function that
	only knows about the base class still calls through the base class's vtable struct type, even
	when the actual object (and its real vtable) is the extension class. This renders fine as long
	as the called slot exists in the base class vtable, but if the extension class introduces a
	virtual function the base class doesn't declare, there's no slot for it in the base struct and
	the call can't be rendered/typed through it properly.
	Not trivial to fix, and no single fix covers every case - depends on whether the registered
	vtables on the member form a chain (Base -> Derived -> Derived2, each one strictly extending
	the previous) or diverge into siblings (Base extended independently by e.g. Reptile and
	Mammal, each adding their own unrelated slot(s) at the same index). Two-tier approach:
		a) Chain case: before assuming the largest registered vtable is a safe stand-in for the
		   member's type, actually verify it - compare slot signatures (not just size) across all
		   registered variants at every shared index. If they all agree, retyping the member to
		   the largest is provably safe (every existing call site renders identically, since the
		   shared prefix is unchanged) and newly-reachable slots render correctly too. Safe to do
		   automatically.
		b) Diverging/sibling case (no total order - "largest" is meaningless, e.g. Reptile and
		   Mammal are both size 2 but slot 1 means something different in each): there's no
		   single statically-correct type, so don't guess - retype the member to a union of the
		   known vtable struct types (one arm per registered variant, reusing the same VTABLE:
		   data SetVtable/JumpToVtable/JumpToImplementation already track) and let the analyst
		   pick the right arm per call site. Rather than expecting Hex-Rays to auto-select the
		   right union member (unreliable/unclear if even possible), provide an action at an
		   unrenderable or ambiguous vtable-slot call that lists the known variants and inserts
		   the appropriate cast at that specific call site when the analyst confirms which
		   subclass it actually is - i.e. automate the manual "change variable type"/cast
		   workaround instead of trying to make Hex-Rays guess it. A wrong automatic guess here
		   is worse than today's behavior: an unrenderable call is an honest "doesn't understand
		   this," but a confidently-wrong slot name (e.g. showing lay_egg() for a call that's
		   actually start_heating_blood()) is a landmine for whoever reads the pseudocode later.

6. Extend 'Commit type' to work on virtual (vtable) calls, not just direct named-function calls.
	Currently it only handles function.op == cot_obj and fails with "Unsupported function
	expression type" on a call through a vtable member.
	Done - differently than originally scoped: instead of resolving to an implementation and
	editing its signature, CommitType now edits the vtable slot's own declared function pointer
	type in the vtable struct (via the new apply_to_vtable_member()), since there's no single
	implementation address for a virtual call and every implementation reached through that slot
	should share the same declared signature.

5. In 'analyze vtable', make the initial dialog box ask for both the vtable struct name, and the type of
	'this', and the name for the vtable symbol. It should provide defaults for all of these, of the
	following format:
		struct name: vtable_<class>
		type of this: <class> *
		symbol: <class>::__vtable
	The 'class' should be determined by a preceding dialog box that asks for the class name (optional).
	If not provided, the class name should be class_<vtable address>
	Done - analyze_vtable() now asks for an optional class name first, then shows a form
	(AnalyzeVtableForm) with struct name / this type / symbol fields prefilled with the
	spec's defaults, and renames the vtable symbol via ida_name.set_name() on success.

4. In 'set vtable comment', after completion, ask if user would also like to perform the analysis.

	Done - added analyze_vtable() (shared with AnalyzeVtable) and set_member_type_to_pointer();
	SetVtable (renamed from SetVtableComment) now asks to analyze right away, and on success
